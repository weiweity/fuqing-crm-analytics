## 1. 一句话与老板期待

> 让公司不只会花钱买来第一单，还能看清怎样把第一单变成后面的生意。AI 把机会查清、把方案准备好，老板决定优先做哪件事、投入多少、什么时候停。

老板需要的是更有依据的经营取舍、更少的跨报表协调，以及有边界的行动。自由问数、分析画布、驾驶舱和数字员工是交付方式，不分别包装成四个项目，也不把聊天界面本身作为创新证明。

第一版主决策：**是否批准一个有边界的天猫内部跨渠道客户增长试点，优先验证一条“首购 → 后续购买”的客户承接路径。**

CEO 决定经营优先级、资源上限、负责人和继续/停止条件；运营负责提出人群与商品方案、核对名单、安排执行和复盘。现有演示按钮的“CEO 审批”名称不等于生产环境中每次名单导出都必须由 CEO 审批；真实角色与权限以后按授权设计。

## 2. 问题与最小业务切口

用户提供的业务条件：天猫内部货架、直播、淘客、小样等成交具有渠道字段，同一 user_id 可以关联。需要从订单计算可观察的首次有效购买，当前不能把订单关联当作真实因果获客归因。

经营主线固定为：**渠道 × 首购商品 × 后续购买**。

- 从“哪个渠道卖得多”走向“不同渠道和商品怎样承接同一批客户”。
- 先发现值得验证的客户路径，不预先认定直播、货架或小样的优劣。
- 数据问题示例：“小样首购客户后来买了什么正装，什么时候买，在哪个渠道买？”它是研究入口，不是小样已经造成正装增长的结论。
- 经营选择包括继续研究、准备试点、不新增营销；不能为了展示 AI 行动而强行推荐触达。

这是基于用户场景的产品判断，不是中国 CEO 偏好排名或本公司已验证的痛点量化调查。稳定 user_id 是可实施条件，不宣称独家技术或行业首创。

## 3. 从问题到拍板材料

| 老板需要的内容 | 首版必须呈现 | 不得冒充 |
|---|---|---|
| 机会在哪里 | 一个明确的渠道、首购商品、人群和后续购买问题 | 全渠道因果获客归因 |
| 为什么值得试 | 同观察期比较、样本量、数据覆盖、口径版本、可核验依据和限制 | 渠道导致了增长、统计不确定性已消除 |
| 准备怎么试 | 候选人群与承接商品、入选/排除条件、待审批行动草案 | 已触达客户或已完成 CRM 集成 |
| 谁负责、投入多少 | 负责人、资源上限、执行范围的待确认项 | AI 代替人批准预算、填写未知成本 |
| 如何继续或停止 | 观察周期、评估指标、对照与成本要求、退出条件 | 已证明真实利润、已确定真实实验样本规模 |

拍板材料是逻辑内容要求，可以复用聊天、画布和现有卡片表达，不新增一套独立审批门户。

演示的目标结尾（示例台词，非真实审批）：

> 下一个经营周期，先把这条客户承接路径验证清楚。由运营负责人牵头，AI 负责分析和准备方案，财务补齐成本口径。在限定范围内试，达到约定标准再扩大，没有效果就停。

## 4. 已采用的产品方式与复用

- 已选择统一分析工作台：纯净 Chat → 有口径与证据的分析画布 → 保存分析 → 驾驶舱或标准 BI 复用。支持在已验证能力与条件内连续追问，不承诺任意自然语言问题都可回答。
- 已选方案之外，不重开独立数字员工平台或通用低代码搭建平台。专家承担业务职责与受控工具组合，不按“一个 API 一个员工”拆系统。
- 保留 Vue/FastAPI、确定性指标和现有 Mission 的可复用资产；是否采用上游原生 Web 聊天界面承载，留给最小改动验证，不在本轮冻结。
- 保留单一在线 Agent 主运行时策略。Hermes 与 DeepSeek Harness 的 UI、接口和安全适配仍待工程验证；此前的优先顺序与最新原生 UI 建议不当作最终选型。
- 保存分析不等于同意营销。新分析只有在条件、人群和数据版本的绑定通过验证后，才能衔接行动草案。否则明确提供独立旧 Mission 演示，不得将其固定人群冒充新分析结果。

取舍记录：仅固定 BI 不能覆盖已确认的追问与保存体验；平台承载可作为复用手段验证，但不扩大为通用搭建产品。此前选择的“统一分析工作台”不因本轮价值收口而重新表决。

## 5. 分阶段承诺与验收

### 当前交付事实

仓库保留合成 Mission 的查询、审批和 DRAFT_EXPORT 演示基线，合同见 [Mission API](./MISSION-API.md)。本轮只收敛文档，没有重新运行应用或测试，因此不把历史验证结果写成本轮验收。

新版多轮工作台、分析保存与驾驶舱复用、上游运行时接入，均不得因本文出现而标为已完成。[接口草案](./ANALYTICS-CONTRACTS-DRAFT.md) 不是可调用接口清单。

### 首版产品验收目标（尚待实现/逐项验证）

1. 使用代码生成的合成数据与 manifest，完成一条渠道 × 首购商品 × 后续购买分析，不固定宣称某渠道最好。
2. 连续追问时沿用明确的人群、时间与口径；歧义先澄清，越界问题明确拒绝或说明缺项，不默默换分母。
3. 对比显示相同观察窗口与成熟度、样本量、订单去重、退款处理和历史覆盖；缺少覆盖时降级为“首次观察到的购买”。
4. 关键数字与独立合成金标准对照；证据能定位到同一数据/口径版本。记录通过、失败和未测试，不复用旧测试数量充当新版结果。
5. 保存后的分析在驾驶舱或标准看板复用时保持一致；不支持的筛选条件明确提示，不悄悄丢失。
6. 行动草案清楚呈现入选/排除条件与数据版本；审批前不导出，审批后最多进入合成 DRAFT_EXPORT，导出与分析人群关联需单独验收。
7. 现场能说明一次经营选择、依据、未知项与退出条件；功能缺失如实标注，不用动画或预置名单假装 AI 已完成整条链路。

### 获得独立授权后才做的业务试点

真实试点必须另行确认人群、负责人、成本、预算上限、期限、触达合规/权限及成功/停止条件。实验分组与观察期依据真实购买周期、样本规模和统计设计确定，不复制演示 90/10 为通用答案。

首先比较分析/核对/形成决策材料的实际耗时及正确性；再以合适的对照和成本核算评估增量购买与增量贡献。未取得成本及干预证据时，不给真实 ROI 或预算最优分配结论。

### 长期愿景

逐步接入授权后的 CRM/短信执行、结果回流和受约束的自动化。这是“无人电商的经营决策雏形”，不是已经实现无人经营；发送成功也不等于产生业务增量。

## 6. 不做与交付边界

- 本轮不改代码、启动服务、安装运行时、调用收费模型、读取/复制/改写真库、发送消息、部署或提交 Git。
- 公开材料和本地比赛数据使用从代码生成的合成数据，不只替换真实 ID。真实归档 DuckDB 继续保持私有与冷存。
- 本地优先，PC2 不纳入；RFM 性能改造暂不作为本轮架构讨论或业务验证的前置，但实际接入分析路径仍需自己的正确性、资源与权限验证。
- 公网部署及访问控制继续待独立确认。用户要求 9 月 10 日前交网址；本地完成不等于网址已提交，不自动通过隧道公开本地免登录环境。
- 比赛提交渠道是作品网址，后续可更新；当前不新增发布流水线。部署和发布验证在独立部署阶段处理。决赛约 10 月，具体时间待赛事确认。
- 不用“L3”、完整客户生命周期、真实渠道排名、自动营销闭环或合成收益金额代替实测证据。

## 8. 独立评审与下一步

前轮独立 CEO 评审指出：老板购买的是有依据的经营取舍，名单导出属于执行环节；订单关联不是因果增长，DRAFT_EXPORT 不是营销闭环。本文件据此把演示落点上移为试点批准。该评审是同模型的独立视角，不宣称跨模型共识。

本书面稿完成两轮五维独立审查：第一轮发现 1 项术语风险，已把主决策明确限定为“天猫内部跨渠道”，配套口语稿和报名文案同步。第二轮完整性、一致性、清晰性、范围、可行性全部 PASS，评分 9.5/10，未留文档自洽性问题。审查未验证实际产品或外部来源；评分仅是文档意见，不是产品质量或业务效果验收。

下一步是一次限定范围的工程收敛：以本文为验收锚点，核对原生 Web UI 最小复用方案、合成分析合同及“分析 → 保存/复用 → 人群草案”的绑定；更新旧工程草案的范围与顺序，再进入获准的实现。不要重新讨论已确认的商业定位，也不要从 RFM、员工市场或公网部署重新扩散。

真实试点所需的负责人、预算和统计参数尚未确定；它们不阻塞合成演示方案，但阻止真实试点执行。
